# Implementation Plan: Instance Overview API — Every Contest Area Readable on Demand

**Branch**: `018-instance-overview-api` | **Date**: 2026-09-29 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/018-instance-overview-api/spec.md` (clarified
2026-09-29, 4 questions)

## Summary

A new application class, `sentai.overview.OverviewService`, answers four things over a **fixed,
compiled area table** (data-model §1): one reading per instance area, an 11-area summary where each
area carries its own outcome, a spec 013 report run on demand, and "turn this area into a flow". All
of it reads the management API with the operator's own token through the helpers that already
return the platform's refusal verbatim (`TaskService.PlatformRead` / `Refusal`) or, for reports,
through the report classes' own `Reader` and `ReadExecutor.Build`. Nothing is stored except, in
User Story 5, an append-only `ProcessAction` record — and User Story 5 starts with a spike that may
end it. Measurements behind every choice are in [research.md](research.md).

## Technical Context

**Language/Version**: ObjectScript (IRIS 2026.2). No frontend change (spec 019).

**Primary Dependencies**: none new. Platform reads (probed 2026-09-29, [R-1](research.md)):
`GET /api/admin/v2/processes`, `…/locks`, `…/monitor/system-usage/shared-memory`,
`…/monitor/system-usage`, `…/monitor/dashboard/main`, `…/monitor/dashboard/system-resources`,
`…/monitor/license-usage`, `…/devices`, `…/web-sessions`, `…/security/users`, `…/web-apps`,
`…/wallet/collections`; US5 only: `POST …/process/suspend|resume|terminate`, `GET …/process?id=`.

**Storage**: one new persistent class, `sentai.model.ProcessAction` (US5 only; storage generated by
the compiler, never hand-edited). No other state.

**Testing**: `%UnitTest` through `zpm "test sentai-task -only"`, platform scripted with
`sentai.unittest.AdminApiDouble` ([R-10](research.md)); new tests flat under
`tests/sentai/unittest/overview/`:
- `AreaTableTest`: the 11 ids, their groups, and that every mapped step type is a catalog
  `platform-read` type
- `ReadingsTest`: each reading's platform paths, allow-lists (no `ID`, `DeleteID`,
  `CSPSessionID`), computed `SMHUsedPercent`, absent fields as null, refusal and silence verbatim,
  unknown names make no platform call, two requests make two platform calls
- `SummaryTest`: 11 entries, the headlines of R-3, one refused or unreachable area leaves the others
  `ok`, the shared dashboard read, a 200 with `status.errors` counts as `refused`
- `OnDemandReportTest`: same findings as `ReadExecutor.Build` for each type, parameter errors give
  422 without a call, non-report types are refused, no `Run`/`StepRun`/`LogEntry` rows are created
- `AreaFlowTest`: the definition of R-8, name suffixing, category fallback, 409 without a step type,
  validation returned
- `OverviewEndpointTest` (rest): routes, token check, `target` refused, status codes of the delta
- `OverviewSecrecyTest`: the SC-006 scan of every answer produced by the tests above
- US5 only, `ProcessActionTest`: 428 with a missing or wrong confirmation and no record, a record on
  accept and on refusal, newest-first read

**Target Platform / Project Type**: as today, an IPM module served by IRIS at `/csp/sentai/api/v1`.

**Performance Goals**: SC-001 < 2 s per reading (slowest measured read 158 ms); SC-002 summary < 3 s
(10 distinct reads in series for 11 areas ≈ 0.57 s measured, [R-3](research.md)).

**Constraints**: only `GET` except US5's three `POST`s; no path, query or field from input; no
cache; allow-listed fields only; platform text verbatim; primary instance only; UI-facing strings
in English.

**Scale/Scope**: ~4 new classes (~450 lines) + 1 persistent class (US5), ~8 test classes (~50
tests), 6 routes, README and limitations sections.

## Decisions

- **D-1 One service, a compiled area table.** `sentai.overview.Areas` holds the table of
  data-model §1 in `XData`, returned by a class method as a `%DynamicArray` (like the step-type
  catalog), so the table is reviewable in one place and testable against the catalog.
- **D-2 Readings are allow-list + arithmetic.** `sentai.overview.Readings` has one method per
  reading: fixed path(s) → `PlatformRead` → `Report.Pick` per row with the allow-list of
  data-model §2 → computed columns listed in `computed`. Missing fields stay null (edge case).
- **D-3 Summary in series, headlines as pure functions.** `OverviewService.Summary` makes the 10
  distinct reads once each (the dashboard read feeds both `activity` and `alerts`), then calls one
  pure `Headline<Area>(result)` per area. Serial reads take 0.57 s measured; workers would add
  complexity for no gain ([R-3](research.md)).
- **D-4 Reuse, not copy.** Readings use `TaskService.PlatformRead`/`Refusal`/`Problem`; reports use
  `Reader` + `ReadExecutor.Build`; parameter checks use `FlowValidator.DeclaredStepFindings`
  ([R-5](research.md), [R-6](research.md)).
- **D-5 Area → flow like the example flow.** `AreaFlow.Definition(area, parameters, token)` builds
  the definition of [R-8](research.md); `AreaFlow.Save(def, user, token)` stores it with
  `Flow.SaveGraph` and returns `{flowId, validation}`. Structural checks (`ValidateStructural`) and the
  answer's shape (`ShapeFlow`) stay in `Dispatcher`, exactly as `POST /flows` does it, so no
  application class depends on the REST layer (Constitution I).
- **D-6 Primary only.** A `target` anywhere in an overview request gives 400 before any call
  ([R-9](research.md)).
- **D-7 Process actions behind a spike.** Increment 5a is the spike (evidence in `evidence/`, in
  spec 001's envelope, no credentials). 5b builds `sentai.overview.ProcessActions` and
  `sentai.model.ProcessAction` only if 5a shows a usable contract; otherwise 5b is replaced by a
  `docs/limitations.md` entry (FR-023). The confirmation check reuses dispatch's 428 wording.
- **D-8 Headline sources.** Licenses come from `license-usage.Summary`, not `dashboard.Licensing`
  (the two disagree; [R-3](research.md)); memory comes from the `Total` row and the most-used
  consumer.
